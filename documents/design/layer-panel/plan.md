## Design

- `request` never touches the store (TR-60); features own the store writes.
- Abort detection: `error.name === 'AbortError'`; aborted loads dispatch nothing, so the UI never shows them (spec 3).
- Latest request wins twice over: the previous controller is aborted, and a result is dispatched only while its own signal is live, so a response that ignores abort is still discarded (spec 12).
- React StrictMode mounts effects twice in dev: the first mount's request is aborted by its cleanup; only the second writes.
- `loadSucceeded` keeps `activeLayerIds` in API order filtered to known ids; if that leaves none and the list is not empty, `[layers[0].id]`.
- Vedro `dispatch` merges top-level keys, so every transition returns the whole `layer` key (PLAN-5).
- Vedro's hooks are used as is; custom hooks only add logic on top of them. Vedro's `useSelector` subscribes in an effect and misses a write made before it subscribes, so a component calls its selectors before `useLoadLayers()`, whose mount effect writes `loading`. `ConnectedLayerPanel` follows this order. Vedro also compares selector results with `JSON.stringify` on every write, which may matter once the timeline changes often (tasks 4 and 5).
- Vedro's `useDispatch` returns a new bound function on every render, so the features call `dispatch` on the store from Vedro's `useStore()`, which is stable; `useLoadLayers`' mount effect then runs once.
- `idle` renders as loading: it lasts only from the first render to the load starting in the mount effect.
- The QA failure switch is kept in `sessionStorage`, so switching it on and reloading shows a failed first load; the QA control is not rendered in test mode, where requests are mocked.
- Production build: `import.meta.env.DEV` is a compile-time constant, so the dynamic imports of `./shared/mocks/*` are dropped; checked by grepping `dist` for `msw` and `QaControl`.
- Tests: `vi.mock('@entities/layer/api/fetchLayers')` with deferred promises to control order and timing; `request` tested with `vi.spyOn(globalThis, 'fetch')`.

## Decisions

### PLAN-5 — One Vedro store, one slice file per entity

- **Status:** active
- **Decision:** A single Vedro store in `shared/store/appStore.ts`, with one top-level key per entity. Each entity keeps its state type, initial state and transitions in its own slice file in `entities/<entity>/model/`.
- **Options considered:** One store per entity with nested providers; one store with all state in one file; one store composed from per-entity slice files.
- **Why:** One store keeps one source of truth (TR-10) and one provider; slice files keep each entity's state next to its business logic, which is the point of FSD (INT-4). Vedro allows it: the state is one object and each slice is one key.
- **Trade-off accepted:** `appStore.ts` imports from `entities/`, an FSD exception allowed for that file only. Every dispatch returns the whole slice key, since Vedro merges only top-level keys.
- **AI involvement:** Claude recommended one store per entity; the user chose one store with per-entity slice files. Claude confirmed in the Vedro source that it works.

### PLAN-7 — No pages layer

- **Status:** active
- **Decision:** No `src/pages/`; `App` keeps the shell grid and renders the widgets directly.
- **Options considered:** A `pages/dashboard/` layer with the grid; the grid in `App`.
- **Why:** The app has only one page, so a pages layer adds a folder with nothing to separate.
- **Trade-off accepted:** If a second page appears, the grid moves out of `App` into `pages/`.
- **AI involvement:** Claude recommended a pages layer; the user rejected it because there is only one page.

### PLAN-12 — Dev mocks and test helpers live in `shared`

- **Status:** active
- **Decision:** The MSW worker, handlers, mock data, failure switch and QA control are in `src/shared/mocks/`; the test setup and shared test data in `src/shared/test/`. Only `main.tsx` and `app/` import `@shared/mocks`, through `import.meta.env.DEV` dynamic imports. The worker script is in `public/`; the build removes it from `dist`.
- **Options considered:** Mocks inside each entity's `api/` segment; a `src/mocks/` folder outside the FSD layers with a dev-only `dev-public/` (Claude's draft); `shared/mocks`, `shared/test` and `public/`.
- **Why:** The user wants them in the lowest FSD layer, and the worker script in the standard `public/` folder.
- **Trade-off accepted:** Mock data in `shared` cannot import entity types, so it is plain JSON-shaped data checked by the app's own response guards; the build needs a small step to drop the worker script.
- **AI involvement:** Claude proposed `src/mocks/` and `dev-public/`; the user changed both.

### PLAN-13 — Requests use plain `fetch`

- **Status:** active
- **Decision:** `request()` is built on the browser `fetch`; no axios, no schema library (SPEC-5 stays).
- **Options considered:** Plain `fetch`; axios; zod for validation; TanStack Query.
- **Why:** Axios would save only the JSON parsing: the `ApiError` mapping and the response checks stay our own code. TanStack Query would keep its own copy of the data next to the Vedro store (TR-10).
- **Trade-off accepted:** About 40 lines of request code and hand-written guards to keep in step with the contract.
- **AI involvement:** The user asked about axios; Claude compared the options and recommended `fetch`; the user chose plain `fetch`.
